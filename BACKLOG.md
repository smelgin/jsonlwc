### Notes

- **Data model.** The component owns a tree of nodes with stable ids and derives the JSON from it, rather than re-deriving rows from the JSON. This is what lets a field's "edited" baseline survive a rename, an insertion, or a deletion that shifts every later array index. Anything touching structure should work with the tree, not with paths.
- **Dependency-free.** No Apex, no static resources. JF-7 and JF-9 would both break that; weigh it deliberately.

#### Design note — ENG-1, Hybrid mode

**What already exists.** Mixing extraction and compliance in one mapping set is not a gap: a rule's `mode` key in the set's Definition takes `Extraction` or `Compliance`, so one set can extract some fields while verifying others, and [`IdpMappingEngine.effectiveMode`](force-app/idp/main/default/classes/IdpMappingEngine.cls) honours it — a rule's own mode beats the run's. So the only genuinely new capability here is the **third bucket: fields handed to custom Apex**.

`IIdpFindingHandler` is the precedent to copy for the plumbing: name an Apex class in metadata, resolve it with `Type.forName`, check it implements the interface, call it, and turn any failure into a finding rather than an exception.

**Decisions taken (Sebastian, 2026-08-16):**

1. **Not a new run mode.** Accept `Custom` in a rule's `mode` key plus a `handlerClass` key on the rule (both in the set's Definition; add them to `IdpConfigLoader.RawRule` and to IDP_CONFIGURATION.md). `normalizeMode` is untouched and there is no fourth run mode — a `Hybrid` run mode would have needed its own hidden fallback for rules that leave `mode` blank, which is exactly what the run mode already provides.
2. **The handler mutates the record itself.** Chosen over the safer transformer shape (return a value, engine writes it) for flexibility. The consequence is recorded below and has to be handled deliberately.
3. **Handlers are skipped in Preview.** Preview is a dry run and custom Apex may have side effects, so handlers do not fire. See the consequence below.

**Consequences of those decisions, to design around:**

- **`plannedChanges` becomes incomplete.** Because handlers are skipped in Preview, anything a `Custom` rule would write is absent from the preview payload. The review UI must say so rather than implying the diff is the whole story — otherwise a user approves a change set that is not what will actually happen. Probably an `INFO` finding naming the skipped rules.
- **FLS and bulk safety move to the handler.** The engine currently guarantees ≤1 DML per run and a query count that does not scale with rows, and `IdpDmlExecutor` applies the FLS checks. A handler holding the record can undo both.

**Still open:**

- **Which kind of mutation.** "Mutate the record" has two readings, and they differ enormously:
    - _Mutate the in-memory `SObject`, engine still flushes it_ — the ≤1 DML property and the executor's FLS checks both survive. **Recommended.**
    - _Handler performs its own DML_ — bulk guarantees are gone the moment a handler is written naively, and the same record may be written twice in one run.
- **Invocation granularity.** Once per run with every matching field, or once per field? Per-field is the obvious API and the dangerous one: a single SOQL inside a handler then scales with row count, which is the property the whole engine was built around. This is the main risk left in the item.
- **The context object.** Something like `IIdpFieldHandler.handle(FieldContext)` carrying the JSON path and field name, the raw and parsed value, the parse grade and confidence, the target record and object, and the section and row info. A context object rather than loose arguments so the signature survives later additions.
- **Ordering.** Whether handlers run before or after ordinary extraction rules on the same record, given both now write to it.
